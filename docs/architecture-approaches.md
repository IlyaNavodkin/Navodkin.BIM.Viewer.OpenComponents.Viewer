# Архитектурные подходы проекта

Этот документ фиксирует архитектурные правила проекта. Их нужно применять по умолчанию при дальнейшей разработке.

## 1. Композаблы как основной способ организации логики

Для каждого значимого компонента создается отдельный composable.

Правила:

- у компонента должна быть своя изолированная логика в отдельном composable
- composable верхнего уровня может собирать внутри себя несколько более мелких composable
- логика не должна разрастаться прямо внутри `.vue` файла, если ее можно вынести в composable

Предпочтительная структура:

- UI-компонент
- его composable
- вложенные composable для узких задач

Пример идеи:

- `ViewerPage.vue`
- `useViewerPage.ts`
- `useViewerToolbar.ts`
- `useViewerSelection.ts`
- `useViewerMeasurements.ts`

## 2. Для каждого composable обязательны интерфейсы

Каждый composable должен иметь явные интерфейсы для входных и выходных данных.

Правила:

- описывать интерфейсы параметров composable
- описывать интерфейсы результата composable
- не передавать набор разрозненных переменных, если можно передать объект composable целиком
- composable нижнего уровня передается в composable верхнего уровня как объект, без декомпозиции на множество отдельных аргументов

Предпочтительный подход:

```ts
export interface IViewerSelectionComposable {
  selectedIds: Ref<string[]>;
  clear(): void;
}

export interface IViewerToolbarComposableParams {
  selection: IViewerSelectionComposable;
}
```

Нежелательный подход:

```ts
useViewerToolbar(selectedIds, clearSelection, selectedCount, setMode);
```

Предпочтительный подход:

```ts
useViewerToolbar({
  selection,
  measurements,
  clipping,
});
```

## 3. Компоненты должны быть тупыми

Компоненты должны быть максимально простыми и декларативными.

Правила:

- компонент в первую очередь отвечает за разметку и привязку UI
- тяжелая бизнес-логика должна жить вне компонента
- некоторые компоненты могут использовать свои локальные composable
- основная связь между состояниями идет через глобальный store

Это означает:

- не строить сложную оркестрацию состояний прямо в `.vue`
- не связывать крупные части приложения напрямую через prop drilling
- общие состояния и координацию держать в store

Роль компонентов:

- получить данные
- показать данные
- пробросить пользовательские события дальше

## 4. Состояние viewer должно создаваться через абстракцию store с уникальным id

Для каждого viewer используется отдельный экземпляр состояния, создаваемый через абстракцию store-фабрики.

Цель:

- избежать конкуренции состояния
- избежать наложения данных при быстром выходе и повторном входе на страницу
- корректно поддерживать несколько viewer одновременно или повторное открытие одного viewer

Правила:

- viewer store не должен быть одиночным глобальным singleton без контекста
- viewer store должен создаваться по уникальному идентификатору
- идентификатор должен однозначно отделять один жизненный цикл viewer от другого

Предпочтительная идея:

```ts
const viewerStore = useViewerStoreById(viewerId);
```

Или:

```ts
const viewerStore = viewerStoreFactory.get(viewerId);
```

Требования:

- при заходе на страницу создается или запрашивается store по `viewerId`
- при уходе со страницы viewer корректно очищает свои ресурсы
- повторный быстрый вход не должен поднимать старое конкурирующее состояние другого экземпляра viewer

## 5. Стилизация только через классы и токены дизайна

Использовать только классы вида `$style.className`.

Правила:

- использовать CSS Modules
- обращаться к классам только через `$style.className`
- не использовать строковые глобальные классы как основной способ стилизации
- классы должны использовать токены из дизайн-системы

Предпочтительный подход:

```vue
<div :class="$style.container"></div>
```

```css
.container {
  background: var(--ds-color-bg-surface);
  color: var(--ds-color-text-primary);
}
```

Ограничения:

- не завязываться на случайные inline-значения, если есть дизайн-токены
- не строить стили вокруг ad-hoc цветов, отступов и размеров, если есть системные переменные

## 6. Не использовать `v-model`

Директиву `v-model` не использовать.

Правила:

- использовать только явные `props`
- использовать только явные `emit`
- поток данных должен быть очевидным

Предпочтительный подход:

```vue
<MyInput
  :value="name"
  @update:value="onNameChange"
/>
```

Нежелательный подход:

```vue
<MyInput v-model="name" />
```

Причина:

- явные `props` и `emit` делают поток данных прозрачнее
- проще контролировать обновления и границы ответственности компонента
- меньше скрытой магии при сопровождении сложного UI

## Практические выводы

Все новые фичи по умолчанию должны проектироваться так:

1. Сначала определяется store-граница и идентификатор сущности, если это viewer или другой stateful-модуль.
2. Затем логика разбивается на composable верхнего и нижнего уровней.
3. Для каждого composable описываются интерфейсы входа и выхода.
4. Компоненты остаются тонкими и UI-ориентированными.
5. Стили пишутся через CSS Modules и токены дизайн-системы.
6. Связь формы и контролов делается через явные `props` и `emit`, без `v-model`.

## Краткая памятка

- composable на компонент обязателен
- вложенные composable допустимы и приветствуются
- интерфейсы для composable обязательны
- composable передаются как объекты
- компоненты тупые
- связь состояний в основном через global store
- viewer store создается по уникальному `id`
- стили только через `$style.className`
- только дизайн-токены
- `v-model` не использовать
